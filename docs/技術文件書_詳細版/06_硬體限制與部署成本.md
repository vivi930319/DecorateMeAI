## 一、模型體積與推論延遲

### 1.1 量測方法

```python
opts = ort.SessionOptions()
opts.intra_op_num_threads = 1     # 單執行緒
opts.inter_op_num_threads = 1     # 逼近 concurrency=6 共用 2 CPU 的最差情況
# 暖機 3 次後，取 20 次平均
```

用單執行緒的理由：Cloud Run 的 `containerConcurrency = 6`，
六個請求共搶 CPU 時，每個請求實際能用的核心數接近 1。
用多執行緒量會得到一個線上永遠達不到的樂觀值。

### 1.2 五種 CNN 架構（輸入 96×96）

| 架構 | 參數量 | ONNX 體積 | 單次推論 | 五部位合計 | 相對 MobileNet |
| --- | --- | --- | --- | --- | --- |
| MobileNetV3-small | 1.5M | **6.1 MB** | **0.6 ms** | 30 MB / 3 ms | 1.0× |
| EfficientNet-B0 | 4.0M | 15.9 MB | 3.4 ms | 80 MB / 17 ms | 5.2× |
| ResNet-50 | 23.5M | 93.9 MB | 14.3 ms | 469 MB / 72 ms | 22.2× |
| **ConvNeXt-Tiny** | 27.8M | 111.2 MB | 19.8 ms | **556 MB / 99 ms** | 30.6× |
| AlexNet | 57.0M | — | — | — | — |

> **參數量與延遲不成正比。** AlexNet 有 57M 參數但多數在全連接層（矩陣乘法，很快）；
> ConvNeXt 只有 27.8M 卻最慢，因為它的計算集中在卷積與 LayerNorm。
> **要看的是 FLOPs 與記憶體存取，不是參數量。**

### 1.3 DINOv2 ViT-S/14

| 項目 | 數值 |
| --- | --- |
| ONNX 體積 | 88.4 MB |
| 單次前向（224×224）| **109.9 ms** |
| 每次分析呼叫次數 | **3 次**（臉型／眼型／鼻型各一次 ROI）|
| 每次分析總成本 | **330 ms** |

**這就是規格書說的「DINOv2 佔整個分析 57% 時間」的真身。**

關鍵實作細節：`predict_dinov2()` 的迴圈是**每個部位各跑一次 backbone**，
不是整張臉跑一次共用：

```python
for part, (coef, intercept, classes, geom) in heads.items():
    tensor = _dino_tensor(frame_bgr, points, part)   # 各自裁 224 ROI
    emb = backbone.run(None, {"images": tensor})[0][0]   # ← 各跑一次
```

所以「多開一個部位用 DINOv2」的邊際成本是 **+110ms**，不是零。
反過來說，把已經在算的部位改成採用它的答案，邊際成本才是零。

### 1.4 換架構的決策依據

```
現況（部署前）  MobileNet×5 (3ms) + DINOv2×3 (330ms)  =  333 ms   映像 118 MB
方案 A          ConvNeXt×5，完全不用 DINOv2            =   99 ms   映像 556 MB
方案 B          EfficientNet×5 + DINOv2×3             =  347 ms   映像 168 MB
```

**選 A：同時變準又變快。** 這種情況很少見——通常換大模型要在準確度與延遲之間取捨。
之所以成立，是因為 DINOv2 那 330ms 買到的眼型 0.625，ConvNeXt 用 20ms 就做到 0.693。

## 二、記憶體：最容易低估的限制

### 2.1 量測方法

不是量「模型檔多大」，而是**跑完整分析路徑**再量行程的 working set：

```python
# 走真實路徑：InsightFace 偵測 + MediaPipe landmark + 五個 ConvNeXt 推論
```

### 2.2 結果

```

```

**遠超模型檔本身的 556 MB。** 差額來自：

| 來源 | 估計 |

本機的 venv 裝了 torch（訓練用），量出來可能被灌水。實際檢查：

## 三、Concurrency：一個被低估的設定

### 3.1 原本的問題

`containerConcurrency = 160` 表示一個實例同時接 160 個請求，但只有 2 顆 CPU。

平常自己測沒感覺（同時只有一個請求），但**口試現場如果五六個人同時上傳，
他們會共搶那 2 顆 CPU**，每個人的等待時間變成好幾倍——
而 `maxScale = 10` 完全用不到，因為 Cloud Run 認為一個實例還吃得下。

### 3.2 為什麼是 6

ML 推論是**計算密集**（CPU-bound），不像 Web API 那樣多數時間在等 I/O。
通常設在 CPU 數的 2～4 倍：4 CPU × 1.5 ≈ 6。

設低的代價是實例數變多（每個實例都要 8Gi），設高的代價是每個請求變慢。
**對展示情境，延遲比成本重要。**

## 四、端到端延遲

### 4.1 本機實測（切換 ConvNeXt 後）


**冷啟動 3.3 秒**是五個 111MB ONNX 的載入時間。這也是 `minScale = 1`

## 五、映像體積與建置

| 項目 | 舊 | 新 |
| --- | --- | --- |
| 五個 CNN ONNX | 30 MB | **556 MB** |
| DINOv2 backbone | 88 MB | **0**（已從白名單移除）|
| 規則樹 + DINOv2 head | ~1 MB | ~1 MB（保留供回滾）|
| 合計模型檔 | ~119 MB | ~557 MB |

**DINOv2 backbone 移出白名單**是因為它退場後就是死重量。
但 head 檔留著——要開回 shadow 對照時只要改環境變數。

> ⚠️ **陷阱：** 真要開回 DINOv2，得先把 backbone 加回 `.dockerignore`
> 與 `.gcloudignore` 兩份白名單，否則 `_load_dinov2()` 找不到檔案會**永久停用**——
> 它只記一行 log，不會拋例外。

### 5.1 ONNX 匯出的一個陷阱

```python
torch.onnx.export(..., dynamo=False)
```

`dynamo=False` 的理由寫在程式註解裡：torch 2.12 的新 exporter 預設會把權重
另外存成 `<name>.onnx.data`，**拆成兩個檔就多一個「少複製一個檔就靜默壞掉」的機會**。

ConvNeXt 是 111MB，實際確認過**仍是單一自帶權重的檔案**（沒有 `.onnx.data`）。

## 六、成本結構

| 項目 | 說明 |
| --- | --- |
| **minScale = 1** | 實例常駐，這是持續計費的主要來源 |
| **8Gi × 4 CPU** | 單位時間成本比 2Gi × 2 CPU 高 |
| **Cloud Build** | 每次部署一次建置費 |
| **Artifact Registry** | 映像儲存，556MB × 保留的版本數 |
| **GCS** | 妝前／妝後圖，物件 30 天 TTL |

具體金額請看 billing console 的實際數字——本文件不報估算值，
因為區域定價會變，而你已經在付 minScale=1 的費用，那是最好的基準。

## 七、可能被問到的

**Q：為什麼不用 GPU？**
Cloud Run 支援 NVIDIA L4，但：(1) 費用高得多；(2) 本專案的推論只要 99ms，
CPU 已經夠；(3) GPU 實例的冷啟動更久。**瓶頸不在算力，在模型載入與 I/O。**

**Q：556MB 的映像會不會太大？**
會影響**冷啟動**，但 `minScale = 1` 讓實例常駐，使用者不會撞到。
真正的限制是記憶體（8Gi）與 Artifact Registry 的儲存費。

**Q：為什麼不用量化（quantization）壓縮模型？**
沒做，是這個專案還沒走到的方向。ONNX Runtime 支援動態量化（INT8），
理論上可以把 111MB 壓到約 28MB、推論也更快，代價是精度損失。
**應該量過再決定**——這是明確的後續工作，不是已完成項目。

**Q：怎麼確認換架構之後線上真的變快？**
`/health` 只證明程序活著。要驗延遲必須**打實際的分析端點並量 `%{time_total}`**，
而且要打兩次以上（第一次含冷啟動）。這個專案的部署驗證流程明確要求這一步。
