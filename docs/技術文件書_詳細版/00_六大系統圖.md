### 關鍵設計決定

| 決定 | 理由 |
| --- | --- |
| **三個分析服務都不開 `allUsers`** | IAM 只綁 `ai-gateway@decorate-me.iam.gserviceaccount.com` 的 `roles/run.invoker`。外面打得到的只有 Gateway，繞過 Gateway 就繞過了 session／CSRF／actor 驗證 |
| **Gateway 用路徑白名單而非黑名單** | `is_path_allowed()` 用 `re.fullmatch`，沒列進 `allowed_paths` 的一律 404。上游新增端點時必須顯式放行 |
| **上游金鑰放 Secret Manager** | `FACE_API_KEY` 以 `secretKeyRef` 注入，不進映像也不進版控 |
| **face-basic 與 face-pro 共用同一個映像** | 靠 `SERVICE_NAME` 環境變數在 `cloud_start.py` 分派（`basic` / `pro` / `suggestion`），一次建置兩支同時更新 |

## 三、API 串接圖（非同步分析的完整時序）

```mermaid
sequenceDiagram
    autonumber
    participant U as 瀏覽器
    participant G as ai-gateway
    participant F as face-basic
    participant S as Firestore<br/>job_store
    participant C as face_corrections

    U->>G: POST /face-basic/v1/face/jobs/basic<br/>multipart: file<br/>Cookie: __session
    Note over G: 1. 驗 session（多槽 cookie）<br/>2. 驗 CSRF<br/>3. X-Expected-Actor 隔離<br/>4. is_path_allowed 白名單

    G->>F: 轉發 + OIDC identity token<br/>+ x-api-key（Secret Manager）
    Note over F: enforce_service_api_key<br/>缺金鑰則拒絕啟動（fail closed）

    F->>F: _read_clean_image<br/>→ sanitize_upload(bytes, mime)
    F->>S: create(job, status=queued)
    F-->>G: 202 {jobId, resultToken, expiresAt}
    G-->>U: 202（同上）

    Note over F: 背景執行緒開始分析

    F->>F: InsightFace 偵測 + 姿態
    F->>F: MediaPipe FaceMesh 468 landmark
    F->>F: face_roi.crop_roi × 5 部位
    F->>F: ONNX CNN 推論（5 個部位）
    F->>F: DINOv2 backbone × 3<br/>（face/eye/nose ROI）
    Note over F: 眼型取 DINOv2 4 類頭<br/>鼻型取「幾何⊕DINOv2」389 維融合頭

    F->>C: apply(result, image_hash)<br/>套用此臉先前的修正
    Note over C: 只存 SHA-256，不存影像<br/>result["_modelRaw"] 保留模型原始輸出
    F->>S: update(job, status=completed, result)

    loop 前端輪詢
        U->>G: GET /face-basic/v1/face/jobs/{id}/result<br/>X-Job-Token
        G->>F: 轉發
        F->>S: get(job)
        alt 尚未完成
            F-->>U: {error: job 尚未完成, status: processing}
        else 完成
            F-->>U: 200 {result, _modelRaw, 分類來源}
        end
    end

    opt 使用者修正
        U->>G: POST .../feedback {眼型: 圓眼}
        G->>F: 轉發
        Note over F: 驗證值必須出自現行分類表
        F->>S: face_feedback 寫入 _modelRaw 當 predicted
        F->>C: remember(hash, corrections)
    end
```

### 為什麼是非同步

同步 `/v1/face/analyze/basic` 仍然保留，但正式流程走 job：
完整分析含 InsightFace + MediaPipe + 5 次 ONNX + 3 次 DINOv2，
在 Cloud Run 的請求逾時下容易被砍。Job 立刻回 `jobId`，前端輪詢。

- Job TTL：`FACE_JOB_RETENTION_SECONDS = 3600`（1 小時）
- 併發上限：`FACE_JOB_MAX_COUNT = 200`
- 單次分析逾時：`FACE_JOB_TIMEOUT_SECONDS = 180`

### 活動圖裡三個非顯而易見的設計

**1. `BORDER_REPLICATE` 重試（B3）**
資料集是截圖裁出的大頭照，臉常貼齊畫面邊緣。RetinaFace 這類 anchor-based 偵測器
需要臉周圍留餘裕才框得住，直接餵原圖**實測有四成漏掉（545/1297）**。
補一圈複製邊框等於把臉「縮小」回偵測器習慣的比例，實測全數救回。

**2. `_modelRaw` 必須保留（G3）**
套用修正快取後，畫面顯示的是使用者的答案。若回饋面板把那個值當成 `predicted`
送回去，訓練資料會變成**模型在確認自己**——集合被自我循環的假資料填滿，
重訓分數憑空變好，而且從外面完全看不出來。

**3. `canonical_label` 在入口正規化（G2）**
`face_corrections` 存的是使用者當初送出的標籤，而分類表後來合併過。
不換的話，一個已經不存在的類別會被寫進結果，一路流到建議 prompt 與渲染 prompt——
那些對照表只認現行類別，查不到就整句略過，**不報錯**。
