# API 測試與整合負責人說明

這份文件不是正式報告書，而是給組員分工用的內部說明。

## 為什麼寫 API 的人之外，還需要一個人測 API

每個負責人當然要寫好自己的 API，但「API 寫好了」不等於「其他組員真的接得起來」。

寫 API 的人通常只會確認自己的程式能跑，例如：

- Ollama 組確認 `/suggest` 可以產生文字
- Replicate 組確認 `/render` 可以產生圖片
- 資料庫組確認會員、收藏、商品可以存取

但整合時常出問題的地方不是單一 API 壞掉，而是：

- 前端送的欄位名稱和後端要的不一樣
- response 格式和文件寫的不一樣
- CORS 沒開，瀏覽器不能打
- port 或 IP 換了沒通知
- 圖片格式是 base64、DataURL、File 還是 URL 沒講清楚
- API 成功時能跑，但失敗時沒有固定錯誤格式
- 回傳中文 key / 英文 key 混用
- Replicate 回傳的是臨時 URL，不是可長期使用的圖片 URL
- PostgreSQL API 可以在自己電腦跑，但別人的電腦連不到

所以 API 測試負責人的工作不是取代寫 API 的人，而是確認「這支 API 對其他人真的可用」。

## API 負責人 vs API 測試負責人

| 角色 | 負責內容 |
|---|---|
| API 負責人 | 寫功能、接模型、接資料庫、修自己的 bug |
| API 測試負責人 | 用前端/測試工具從外部呼叫，確認大家真的接得起來 |

簡單說：

```txt
API 負責人：我的服務有做出來
API 測試負責人：你的服務別人真的能用
```

## API 測試負責人要測什麼

每個 API 至少要測：

1. `/health` 能不能打開
2. 正式 endpoint 能不能從別台電腦呼叫
3. request JSON 是否和約定格式一致
4. response JSON 是否和約定格式一致
5. 成功狀態是否有 `status`
6. 失敗狀態是否有 `error`
7. 是否有 CORS 問題
8. 圖片欄位格式是否清楚
9. timeout 時前端會不會整個壞掉
10. API URL、port、IP 是否有記錄

## 每個組員 API 最低要求

每個 API 組員都要交：

```txt
1. health URL
2. endpoint URL
3. request 範例
4. response 範例
5. 錯誤 response 範例
6. 是否需要 token
7. 是否支援跨電腦連線
```

## 建議測試紀錄格式

```txt
API 名稱：
負責人：
測試日期：
URL：
Method：
測試結果：成功 / 失敗
錯誤訊息：
備註：
```

範例：

```txt
API 名稱：Ollama 文字建議
負責人：A
測試日期：2026-06-12
URL：http://192.168.1.23:9001/suggest
Method：POST
測試結果：成功
錯誤訊息：無
備註：可回傳 suggestion，但目前還是純文字，尚未拆成 base/brow/eye/blush/lip
```

## 為什麼這個角色重要

七個人一起做專題時，最容易發生的問題是每個人都說「我這邊好了」，但最後整合時才發現：

- 前端接不上
- API 格式不一致
- 圖片 URL 不能用
- DB 沒存到
- 模型端沒有回傳固定欄位

如果等到最後 demo 前才測，會很難修。

所以 API 測試負責人要做的是每天或每兩天測一次，把問題提早抓出來。

## 結論

負責寫 API 的人仍然要測自己的功能。

但需要一個 API 測試與整合負責人，專門站在「其他組員要怎麼使用這支 API」的角度做測試。

這樣可以避免最後整合時才發現大家的 API 規格不一致。
